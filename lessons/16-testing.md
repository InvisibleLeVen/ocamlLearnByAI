# 第 16 课：测试（Testing）

日期：2026-11-20（重讲版）
教材：CS3110 第 8 章 Correctness，8.4–8.6（Testing / Property-Based Testing / Test-Driven Development），补 3.3 OUnit。
说明：本讲义所有代码与输出已于 2026-11-20 用 OCaml 5.5.2 实际运行核对（含 `-noassert` 对照）。

## 0. 一句话

**测试 = 用具体输入执行规格，看输出是否符合 `ensures`。**

第 15 课写的是“应该怎样”（`requires` / `ensures`），测试检查的是“实际怎样”。两者是一对：没有规格，测试不知道期望值从哪来；没有测试，规格只是一纸声明。

## 1. 单元测试：`assert`

给 `clamp` 写测试。规格是：结果落在 `[lo, hi]` 内；`x` 本来就在范围内时原样返回。

```ocaml
(** [clamp lo hi x] requires [lo <= hi].
    ensures the result is between [lo] and [hi];
    if [lo <= x <= hi], the result is [x]. *)
let clamp lo hi x =
  if x < lo then lo
  else if x > hi then hi
  else x

let () =
  assert (clamp 0 10 5 = 5);      (* 范围内 → 原样 *)
  assert (clamp 0 10 (-3) = 0);   (* 低于下界 → lo *)
  assert (clamp 0 10 42 = 10);    (* 高于上界 → hi *)
  assert (clamp 0 10 0 = 0);      (* 恰好等于下界 *)
  assert (clamp 0 10 10 = 10)     (* 恰好等于上界 *)
```

实际运行第一段输出：

```
clamp: 5 条单元测试全部通过
```

要点：

- 每条 `assert` 是一个“输入 → 期望输出”对；断言的是**规格承诺的部分**，不是实现的细节。
- 任一条不成立，运行时抛 `Assert_failure` 异常，程序停止。失败信息只给出表达式，不告诉你“哪条用例、期望什么”——这正是后面 OUnit 要解决的问题。
- `assert` 的局限：编译器加 `-noassert` 会把所有 `assert` 直接编译成 `()`。实测同一文件加 `-noassert` 后，本该失败的强性质也没有失败（见第 4 节输出对比）。所以 `assert` 是开发期工具，不是安全机制。

## 2. 用例从哪里挑

测试的难点不是“写断言”，而是**挑输入**。按输入空间的“危险位置”挑：

| 类别 | `clamp 0 10 _` 的例子 | 想抓的错误 |
| --- | --- | --- |
| 范围中间 | `5` | 常规分支 |
| 恰好等于边界 | `0`、`10` | 确认边界归入范围内、返回 `x` 本身 |
| 边界外一格 | `-1`、`11` | 比较方向写反 |
| 远离边界 | `-3`、`42` | 返回错值（返回 `x` 而不是 `lo`/`hi`） |
| 退化区间 | `clamp 3 3 2`（`lo = hi`） | 两条分支都成立的顺序问题 |

共同点：这些输入会让**某个分支走不到、或让边界判断差一**。四条“正常情况”的用例几乎测不出任何 bug，因为正常情况通常被第一条分支就处理掉了。

注意：对 `clamp`，把 `<` 写成 `<=` 在边界上返回同一个值，这类变异**测不出来**（2026-11-20 实测）；但对 `count_positive` 式的谓词边界（`h > 0`），`>` 误写成 `>=` 只能靠恰在边界的用例（输入 `0`）抓到。

## 3. 黑盒与白盒

- **黑盒测试**：只看规格（`requires` / `ensures`），不看实现。挑用例的根据是“输入空间里哪里危险”和“规格要求什么”。
- **白盒测试**：看实现，按分支、路径挑用例，目标是把每条分支都执行到（“覆盖率”）。

对 `clamp` 来说：

- 黑盒会给 `5`、`0`、`10`、`-1`、`11`、`lo = hi`——这些直接从规格里推出来。
- 白盒看到实现有三个出口（`x < lo`、`x > hi`、`else x`），于是专门为每个出口各造一条用例，并检查有没有出口永远走不到。

白盒的问题：**测试的是实现，可能把 bug 当作“正确行为”固定下来**。如果实现漏了某个规格要求的特例，只看实现写的测试通常也不会想到它。所以两者都要：黑盒检验“行为对不对”，白盒检验“代码有没有被充分执行”。

## 4. 性质测试（property-based testing）

单元测试一条条列；性质测试写“对所有输入都成立”的定律，交给工具生成大量输入自动验证。

例子：`append` 的定律 `length (append l1 l2) = length l1 + length l2`。

```ocaml
let rec length = function [] -> 0 | _ :: t -> 1 + length t

let rec append l1 l2 =
  match l1 with [] -> l2 | h :: t -> h :: append t l2

(* 假实现：丢掉第二个列表 *)
let append_bad l1 _ = l1
```

一个先想清楚再写：`append_bad` 满足下面这条性质吗？

```ocaml
let property_weak (l1, l2) = length (append_bad l1 l2) >= length l1
```

实测：对 `([], [])`、`([1], [2;3])`、`([1;2], [3])` 全部通过。因为丢掉元素只会让长度变短，“长度不小于第一个列表”对假实现也成立。**性质太弱**。

换成强性质：

```ocaml
let property_strong (l1, l2) =
  length (append_bad l1 l2) = length l1 + length l2
```

实测立刻抛 `Assert_failure`。输出对照：

```
append_bad: 弱性质全部通过（假实现未被抓到）
append_bad: 强性质立刻失败，抛出 Assert_failure
--- 加 -noassert 后 ---
append_bad: 弱性质全部通过（假实现未被抓到）
append_bad: 强性质也未失败（不应发生）   ← 断言被整体移除
```

工具（QCheck）做的事就是把手写的 `List.iter` 换成随机生成器，自动生成成百上千个形状各异的列表，并在失败时缩小到最小反例。但工具再强，也只能验证**你写的这条性质**——性质写弱了，工具跑一万次也抓不到假实现。

## 5. 测试与 `requires` 的关系

测试用例必须是规格允许的输入。对 `clamp 10 0 5` 这种违反 `requires [lo <= hi]` 的调用，规格什么都没承诺，实测得到 `10`——这既不是 bug，也不是“正确”，只是**没有意义**的观察。把这类调用写进测试，等于拿未定义行为当期望值。

## 6. 测试不能证明正确

- 输入空间通常无限，你只跑了有限子集；
- 性质测试也只是“有限随机样本 + 一条性质”；
- 测试通过只说明“这些输入上符合预期”，不能说明“所有输入上都正确”。

这正是模块 5 剩余部分（第 17 课）要解决的问题：用**归纳证明**覆盖所有输入，覆盖有限测试够不到的地方。

## 7. 常见误解

| 误解 | 实际情况 |
| --- | --- |
| 测试全过了，函数就是对的 | 只覆盖了测过的输入；反例可能藏在没测到的地方 |
| 用例越多越好 | 重复同类用例收益极低；要覆盖边界与分支 |
| 性质测试能替代单元测试 | 性质可能太弱（`append_bad` 的例子）；两者互补 |
| 性质测试通过 = 性质足够强 | 只能证明“这条性质在这个实现上成立” |
| `assert` 是安全机制 | `-noassert` 可整体关闭；只用于开发期 |
| 违反 `requires` 的调用也能拿来测 | 规格没有承诺，结果没有参考价值 |

## 8. 本课要点

1. 单元测试 = 规格内的输入 + 期望输出 + `assert`。
2. 用例按“危险位置”挑：范围中间、恰好边界、边界外一格、退化情况。
3. 黑盒从规格推用例，白盒从分支推用例；都要用。
4. 性质测试写定律；性质不足够强就抓不到假实现。
5. 测试提高信心，但不证明正确性；正确性留给归纳证明。
